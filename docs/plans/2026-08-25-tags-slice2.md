# Tags Slice 2 — N-way merge write path Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use eng:subagent-driven-development to implement this plan task-by-task.

**Goal:** Make a multi-valued tag dimension (caldav `categories`) reorganizable in `organize` — a membership add/remove per bucket placement — by replacing the single-valued assignment model with an N-way (set) merge, with single-valued dimensions falling out as the N=1 degenerate.

**Architecture:** The document projects each object to a SET of grouped-dimension buckets (not one value). Apply computes a per-object membership set-diff (base → edited); each add/remove routes through the tag interpreter's `Complete` (naive: append/drop the exact tag) to produce the object's new full tag set, which the caldav codec persists as its `CATEGORIES`. Single-valued facet dimensions (status/date/priority) stay on their existing `FacetWriteApplier` completion; the placement-diff engine is unified, the write-completion dispatches by field kind. Every existing single-valued organize lane must stay green (the N=1 conformance pin).

**Tech Stack:** Go; `internal/organize` (document + apply), `internal/cutting_garden_plugins` (`TagInterpreter`, unified field codecs), `plugins/caldav` (codec write side); bats against `cutting-garden-caldav-testserver`.

**Rollback:** No dual period (matches #230/D8). Lands as one merge; rollback is `git revert` of that merge. Safe because the N=1 degenerate is conformance-pinned by the untouched single-valued organize bats before tags ever use the general case.

**References:** design D8 (`docs/plans/2026-08-20-tags-design.md`), RFC 0019 (`Complete`, §5 naive), RFC 0015 (organize dialect), FDR 0023 (organize), FDR 0025 (unified field codecs, `DeriveNodeTypeFacetWrites`).

**Prerequisite reading for the implementer (exact signatures this plan does NOT reproduce — read before Task 2/3):**
- `internal/organize/apply.go` — `planMoves`, `resolveWrites` (296-328), `checkMoveWritable` (388-409), the apply driver that calls them.

## Design decisions settled going in

- **D4 (rendering) is NOT in this slice.** Slice 2 keeps the current `## =<tag>` bucket spelling. The no-`=` continuation rendering (D4 → decision A) lands with the tag-kind rendering in Slice 3, together with the dodder-hyphen interpreter. Building the write path against today's spelling avoids re-spelling a just-built parser.
- **D5 (`_` lift) is a no-op here.** naive `Normalize`/`SortKey` are already the identity; there is no lift to implement or avoid.
- **Dup-guard resolution.** `document.assignments()` (document.go:382-421) rejects an object under two buckets. That guard is single-valued-correct and MUST stay for single-valued dimensions, but is exactly what blocks a multi-membership apply. Slice 2 introduces a cardinality-aware membership projection: multi (`FacetWriteMany`) → several buckets per object is legal; single (`one`) → two buckets is still the loud error. See Task 1.
- **Write dispatch.** Tag-field membership edits complete through `TagInterpreter.Complete` → new tag set → caldav `CATEGORIES` write-back. Facet-enum edits keep their `FacetWriteApplier` completion. The placement-diff (Task 2) is shared; the completion branches on field kind.
- **Removal.** Deleting a line under a bucket removes that membership PROVIDED the object still appears elsewhere in the document. An object's LAST line vanishing stays #215's `%:allow-deletion` territory (unbuilt) and is rejected as today.

## Task 1: Cardinality-aware membership projection

**Promotion criteria:** `assignments()` (single-valued map) is retained only as the `cardinality == one` path; once every caller uses the new projection, the standalone method can be folded in. Keep it until Task 4 lands.

**Files:**
- Modify: `internal/organize/document.go` (add `memberships()` beside `assignments()`; do NOT delete `assignments()` yet)
- Test: `internal/organize/document_test.go`

**Approach:** Add `func (doc document) memberships(multi bool) (map[string][]string, error)`. It walks the same depth-stack as `assignments()` but collects a SLICE of bucket values per id. When `multi` is false it enforces the existing single-value guard (a second DISTINCT bucket for an id is the "appears twice" bad request); when `multi` is true, several distinct buckets are legal and accumulate, but the SAME bucket twice for one id is still malformed (a duplicated line). Ungrouped objects contribute an empty membership set.

**Step 1 — failing test (multi allows several buckets, rejects same-bucket dup):**

```go
func TestMemberships_MultiValued(t *testing.T) {
	doc := document{Sections: []section{
		{Depth: 1, Term: "categories="},
		{Depth: 2, Term: "=work", Lines: []objectLine{{ID: "t1.ics"}}},
		{Depth: 2, Term: "=urgent", Lines: []objectLine{{ID: "t1.ics"}}},
	}}
	m, err := doc.memberships(true)
	if err != nil {
		t.Fatalf("multi membership must be legal: %v", err)
	}
	got := append([]string(nil), m["t1.ics"]...)
	sort.Strings(got)
	if len(got) != 2 || got[0] != "urgent" || got[1] != "work" {
		t.Errorf("t1 memberships = %v, want [urgent work]", got)
	}

	// same bucket twice for one id is still malformed
	dup := document{Sections: []section{
		{Depth: 1, Term: "categories="},
		{Depth: 2, Term: "=work", Lines: []objectLine{{ID: "t1.ics"}, {ID: "t1.ics"}}},
	}}
	if _, err := dup.memberships(true); err == nil {
		t.Error("same bucket twice for one id must reject")
	}
}
```

## Task 2: N-way membership merge (`planMemberships`)

**Promotion criteria:** subsumes `planMoves` for the grouped dimension; `planMoves` is retired when Task 4 routes single-valued through the N=1 path of this merge.

**Files:**
- Create: `internal/organize/membership_apply.go`
- Test: `internal/organize/membership_apply_test.go`

**Approach (refined during execution):**
`planMemberships(edited, base document, live []cgp.Node, anchor string, interp cgp.TagInterpreter, dim string) ([]membershipEdit, error)`, where `membershipEdit{URI string; Node cgp.Node; NewTags []string}` carries the complete replacement tag set to persist. Mirror `planFieldEdits`' base/edited/live-by-id structure (`relativeID`). For each id in base ∩ live: `adds = editedSet \ baseSet`, `removes = baseSet \ editedSet` (sets from `memberships(true)`); fold removes then adds through `interp.Complete(newTags, op, bucket)` starting from the LIVE tag set (`node.Facets[dim]` `.Key`s) → `NewTags`.

- **No hard conflict path in this slice.** Tag add/remove commute and `Complete` is idempotent, so folding the doc's set-diff onto the live set is a sound merge; a bucket a concurrent edit already changed becomes a no-op. If `NewTags` is set-equal to the live set, emit nothing.
- **Last-line-vanish = id ABSENT from the edited doc entirely** (was in base, its line deleted) → reject (`#215`). An object still present but moved out of every bucket (present ungrouped ⇒ id IS in `edited.objectLines()`, empty membership) is a LEGAL remove-all (empty `NewTags`), not this case.
- **Atom reconciliation is DEFERRED to the wiring task (Task 4)** — a multi-membership object's several appearances feeding the existing `planFieldEdits` need dedup/agreement handling there; Task 2 is membership-only.

**Steps:** TDD each rule as its own failing test → minimal impl → pass → commit:
- add-only: base `{work}`, edited `{work,urgent}`, live `{work}` → `NewTags {work,urgent}`.
- remove-with-survivor: base `{work,urgent}`, edited `{work}`, live `{work,urgent}` → `NewTags {work}`.
- no-op: base == edited → no edits.
- idempotent: live already `{work,urgent}` for an add of `urgent` → no edit.
- last-line-vanish (id absent from edited) rejects.
- remove-all-legal (present ungrouped) → one edit, empty `NewTags`, no error.

Commit once green (frequent commits).
