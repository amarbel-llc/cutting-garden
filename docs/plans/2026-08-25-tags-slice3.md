# Part A — dodder-hyphen semantics (fully specified; execute now)

## Task A1: The `dodder-hyphen` interpreter builtin

**Files:** `internal/cutting_garden_plugins/tag_interpreter.go` (+ its `_test.go`).

**Approach:** add `dodderHyphenTagInterpreter struct{}` implementing `TagInterpreter` per RFC 0019 §6/§7, and register it in `tagInterpreterRegistry` under `"dodder-hyphen"`. Semantics (verbatim from the RFC — read §6 for the normative text):
- `Normalize` — identity (`_` literal, no lift, §7). `SortKey` — plain lexical (a leading `_`/`_ ` sorts high naturally, §7).
- `Buckets(tags, namespace)`:
  - empty namespace → WHOLE-DIMENSION: one membership per distinct tag, `Bucket == Via == tag` (same as naive).
  - non-empty namespace `N` → NAMESPACE ROLLUP: for each tag that is `N` or `N-<rest>`, bucket by the IMMEDIATE next segment (`Bucket == "-"+<immediate segment after N>`, per D4's continuation form; `Via ==` the producing tag). Tags not under `N` contribute nothing. Deduplicate by `Bucket` per node (a coalesced bucket's `Via` is any one contributor).
- `Matches(tags, term)` — TRANSITIVE: true iff `term` equals a tag OR is a segment-prefix of some tag (`project` matches `project-client-acme`; segment boundary is `-`, so `pro` does NOT match `project`).
- `Complete(tags, op, bucket)` — at a rollup bucket `-<seg>` under namespace `N`, `TagAdd` appends the namespace tag `N-<seg>` (the only unambiguous leaf the rollup names, RFC 0019 §6.2); `TagRemove` drops every tag under `N-<seg>`. At a whole-dimension bucket (a full tag), add/remove that exact tag (naive-like). Set semantics (idempotent).

**TDD** (mirror the RFC §6 testing table, and `tag_interpreter_test.go`'s naive cases): rollup + `Via` (`project` over `project-cutting_garden`/`project-client-acme`/`project-client-baxter` → buckets `-cutting_garden`, `-client`; `-client` coalesces acme+baxter); transitive `Matches`; `Complete` at `-client` appends `project-client`; `_` literal; empty-namespace whole-dimension parity with naive.

# Part B — namespace grouping UI

Part B is the organize GROUPING surface for tag hierarchies. **Design decisions RESOLVED (2026-08-25, user):**

- **Group-by grammar: bare = tag, `=`-suffix = field.** A bare `--group-by <arg>` resolves as a TAG dimension or tag-namespace when one exists (`--group-by categories` = whole tag dimension; `--group-by project` = the tag namespace `project`, drill deeper `--group-by project-client`); otherwise it resolves as a field/facet dimension (so existing bare `--group-by status`/`date_due`/`priority` are unchanged). A trailing `=` (`--group-by project=`) FORCES the field reading, disambiguating the rare case where a name is both a tag and a field. This mirrors the document dialect exactly (tag buckets drop `=`, field dimensions keep it) and the trellis bare-vs-`field=` grammar.
- **Dimension heading HOISTED for tag groupings.** No `# categories=` / `# project=` parent heading — a tag grouping is just its buckets. **Round-trip consequence:** apply can no longer recover the grouped dimension+namespace from the heading (as it does for `# status=`), so the grouped-by spec MUST be recorded in the document ENVELOPE (a new `- _group_by = <spec>` directive, e.g. `_group_by = project`), which `groupedSpec()`/apply read instead of the heading. Bucket spelling: `## work` (flat tag), `## -client` (namespace continuation), quoted when a value carries a space (`## "_ inbox"`).

## Task B1: group-by resolution (bare→tag/namespace, `=`→field)

**Files:** `internal/organize/groupspec.go` (`parseGroupSpec`) + tests.
Resolve a bare arg to a tag dimension/namespace when it matches one (probe the plugin's tag dimensions + the interpreter's declared namespaces), else a field dimension; a trailing `=` forces field. Extend `groupSpec` to carry the grouping KIND (field vs tag-whole-dimension vs tag-namespace) + the namespace. Keep every existing bare field group-by resolving to the field (no tag match → field).

## Task B2: namespace rollup grouping

**Files:** `internal/organize/group.go` (`groupNodes`) + generate.
When the spec is a tag-namespace grouping, compute buckets via the resolved interpreter's `Buckets(nodeTags, namespace)` (rollup + `Via`) instead of the whole-dimension FacetValue path. Whole-dimension tag grouping stays one-bucket-per-tag. Facet dimensions unchanged.

## Task B3: hoisted continuation-heading dialect + `_group_by` envelope

**Files:** `internal/organize/generate.go` (`dimensionSections`/`buildDocument`), `internal/organize/document.go` (render/parse: `isValueTerm`/`isDimTerm`/`parseBody`, `groupedSpec`, `memberships`/`assignments`).
Render a tag grouping with NO parent dimension heading and no-`=` buckets (`## work` / `## -client`, quoted for spaces); record the grouped spec in a `- _group_by` envelope directive. Parse the no-`=` tag buckets and recover the spec from `_group_by` (not the heading). Ensure `memberships()`/`assignments()` id-resolution round-trips the new bucket spelling. This is the trickiest task — pin render↔parse round-trip and the field-dimension path staying `# dim=`/`## =value`.

## Task B4: rollup write-back

**Files:** `internal/organize/membership_apply.go` / `apply.go`.
Namespace-aware `planMemberships`: for a rollup-bucket ADD, reconstruct the namespace tag (namespace + segment: `-client` under `project` → `project-client`) and exact-`Complete`-add; for a REMOVE, enumerate the object's tags under the bucket's namespace path and exact-`Complete`-remove each (per RFC 0019 §6.2, the exact-`Complete`/apply-owns-reconstruction contract). Whole-dimension tag apply is Slice 2's path unchanged.

## Task B5: end-to-end bats

**Files:** `zz-tests_bats/` (a fixture with hierarchical `project-*` categories).
`--group-by project` renders `-<segment>` rollup buckets with no parent heading; moving an object between rollup buckets writes the reconstructed namespace tag; `--group-by project=` (if a `project` field existed) forces the field reading; whole-dimension `--group-by categories` still works.
